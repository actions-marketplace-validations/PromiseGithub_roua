Most “read-only” accounts aren’t.

Hidden write paths

A role it inherits, a table it owns, a procedure it can run, a default grant: any one of them turns “read-only” into read-write.

Secrets in plain sight

Password hashes, API tokens, card numbers and MFA seeds sit in ordinary columns that a plain SELECT can read.

Never switched off

The demo ends, the contractor leaves, the agent is retired. The account stays, and forgotten accounts are where breaches start.

What every ROUA guarantees, on every database

  1. No write path of any kind. No writes, no schema changes, no procedures, no ownership, no roles that could add them.
  2. Never reads secrets. Secret-looking columns are hidden automatically; you add anything the detector misses.
  3. An owner and an expiry. Every account names who is accountable and switches itself off on a date.
  4. Instant revoke. One script locks the account and ends its open sessions.
  5. Checked before handover. An audit script proves all of the above. Run it any time, on any account.

Know the limits

        
    
          
  • Read-only is not “nothing leaves”. Anything the account can read, the agent can repeat. Scope it to what the agent should know.
    • 
          
  • Expensive queries are still possible. Use the connection and time limits, and a small warehouse on cloud warehouses.
    • 
          
  • Applications need their own guard. For demo and app-review accounts that click through your app, pair ROUA with ROUA-App, which blocks writes at the API.

Questions

    
Is it safe to type a password into this page?
      
Yes. The page is a single file that runs entirely in your browser. Its security policy forbids every network request, so nothing you type can be sent anywhere. You can save the page and use it offline. Where the database accepts it, the scripts contain only a password hash (PostgreSQL, MySQL, MariaDB, SQL Server, Redis), never the password.

    
Why not just use GRANT SELECT ON *.*, db_datareader or a built-in read role?
      
Built-in read roles cover every table, including tables created next year, and they include tables full of secrets. They also leave whatever else the account inherited untouched. ROUA starts from nothing, grants read per table as it exists today, hides secret columns, denies writes explicitly where the database supports it, and adds an expiry.

    
What happens when the account expires?
      
PostgreSQL: the password stops working (VALID UNTIL), and roua expire ends open sessions. MySQL and MariaDB: a scheduled event locks the account and ends its sessions. SQL Server: an Agent job disables the login. Oracle: a scheduler job locks the account. Snowflake: DAYS_TO_EXPIRY. BigQuery: query rights end through an IAM condition. MongoDB and Redis have no scheduler, so you schedule the revoke script; the audit flags it if you forget.

    
Does it work with managed databases?
      
Yes, as long as you have an administrator account: Amazon RDS and Aurora, Google Cloud SQL and AlloyDB, Azure SQL and Azure Database, Supabase, Neon, Oracle Autonomous Database and others. Each database in the table above lists the services it covers. Some checks that need superuser (such as reading pg_hba.conf) report a warning instead.

    
Does read-only stop data from leaving?
      
No, and nothing that can read can promise that. Read-only means the account cannot change or destroy anything. Decide what it may see with the scope, the exclusions and, on PostgreSQL, masking.

    
Can I use this in automation?
      
Yes. On PostgreSQL, the roua CLI plans, applies, verifies and revokes accounts from a roua.yaml file (npx @roua-dev/cli audit --role readonly), also as a Docker image (ghcr.io/promisegithub/roua). The GitHub Action fails a build when an account stops being read-only. AI agents can use the ROUA MCP server. For other databases, the generated scripts are plain files you can keep in version control and run in a pipeline.

    
Who is behind ROUA?
      
The term ROUA (Read-Only User Account) was coined by Promise Okoroji. ROUA is an open standard (draft 0.1) with Apache-2.0 tools. Reviews of the spec, bug reports and attempts to break the audit are very welcome on GitHub.
